## The Deterministic Core: Foundation for Financial Safety and Reliability

The central finding of this research is that the optimal architecture for the 'Buy or Wait?' challenge is a hybrid model centered on a **deterministic financial core** [[13]]. This approach prioritizes predictable, rule-based computation for all financial reasoning tasks, while using AI selectively for interpreting unstructured data. This philosophy is grounded in the nature of the problem, historical competition outcomes, and established engineering best practices. The challenge requires adherence to strict, well-defined constraints governing 90-day safety simulations, payment plans, currency conversion, deadlines, and evidence grounding [[1,16]]. These are not open-ended creative problems but complex logic puzzles and optimization problems that demand reproducible and verifiable solutions [[4,6]]. A deterministic model, defined as one where outputs are entirely determined by inputs with no randomness, aligns perfectly with these requirements [[5,7]]. In contrast, fully autonomous agentic systems introduce non-determinism through LLM behavior, which can lead to unpredictable results and schedule-dependent bugs, a known risk in parallel programming contexts [[36]]. Analysis of previous Orchestrate challenges shows that submissions often fail due to brittle logic and poor handling of edge cases, with common failure modes including incorrect output formatting and row-order corruption [[13,15]]. Top-performing architectures frequently involve clear, rule-driven pipelines rather than complex multi-agent systems, underscoring the value of determinism [[13,20]]. For instance, a winning solution from a similar verification task explicitly used a "deterministic 'safety gate'" to protect against adversarial inputs, highlighting the critical role of guardrails around any AI components [[20]].

To maximize score, certain components of the system must remain strictly deterministic. These form the non-negotiable foundation upon which the entire solution is built. Any error in these areas would constitute a fundamental flaw in financial reasoning. First, **Financial State Reconstruction and Forecasting** must be a deterministic simulation. This involves accurately calculating the available balance, accounting for confirmed future income, recurring expenses, essential spending, and pending payments [[59]]. The 90-day forecast engine must produce a dated ledger of transactions and balances, ensuring the core invariant—that the user's balance never falls below their minimum required amount—is satisfied at every point in the simulation horizon [[4,53]]. Second, all **Arithmetic and Date Calculations** must be handled by deterministic code. This includes deriving `amount_safe_to_pay`, determining `earliest_date_for_full_payment`, and performing currency conversions. Using an LLM for such calculations introduces unnecessary risks of logical errors and floating-point inaccuracies [[65]]. Third, **Payment Plan Generation and Validation** must be rule-based. The system must generate candidate plans (full payment, partial payment, installments, wait) based on supplied options and validate each one against all constraints, such as installment schedules, fees, and partial-payment rules. An LLM inventing a financing schedule would violate the explicit problem constraints [[55]]. Fourth, the application of all **Constraints and User Preferences** must be deterministic. This includes enforcing the `desired_completion_date`, respecting the maximum of three allowed spending changes, and honoring the user's `payment_methods_user_will_consider`. Fifth, the **Plan Ranking and Selection** logic must be implemented as a deterministic function that follows the official priority order: completion by deadline, minimizing spending changes, minimizing total amount paid, starting earlier, having fewer payments, and selecting the lowest `payment_option_id` [[13]]. Finally, the **Conflict Resolution** mechanism, which applies precedence rules for contradictory information (e.g., explicit cancellation overrides amendment, newer records override older ones), must be a deterministic decision tree [[15]]. The table below summarizes the key components that must remain deterministic.

### Integrated detail retained from companion blueprint — Core Architectural Philosophy: A Deterministic Financial Engine Augmented By Targeted Ai

The foundational decision for constructing a competitive solution to the 'Buy or Wait?' challenge is the adoption of a specification-first, deterministic financial core augmented by a targeted artificial intelligence layer for semantic interpretation. This architectural choice is not an implementation detail but the central pillar of a strategy designed to maximize correctness, ensure constraint compliance, and achieve robust performance against hidden test cases. The nature of the problem, with its explicit rules governing financial simulation, payment plans, currency conversion, and conflict resolution, makes it fundamentally unsuited for end-to-end probabilistic reasoning [[1,2]]. Delegating these score-critical components to a Large Language Model (LLM) introduces non-determinism, which is antithetical to the goal of producing reproducible and reliable results [[5]]. The optimal approach, therefore, is one where the AI's role is strictly confined to interpreting unstructured human communication, while the core financial logic remains entirely deterministic.

The case for a deterministic core is unequivocally supported by the challenge requirements. The mandate to perform a 90-day safety simulation is a classic constraint-satisfaction and forecasting problem [[1]]. The system must generate a timeline of future balances and verify that the minimum balance is never breached after essential expenses are paid [[2]]. This requires precise arithmetic and date calculations, which are strengths of deterministic code. Allowing an LLM to simulate this forecast would introduce variability in its output due to differences in model versions, prompts, or even minor fluctuations in its internal state, leading to unpredictable failures on unseen test data [[6]]. Similarly, the validation of payment plans is governed by rigid mathematical and logical rules. For partial payments, the sum of two payments must exactly equal the requested amount (`payment_1 + payment_2 == requested_amount`) [[2]]. Installment plans must perfectly replicate a schedule supplied in a dataset, and spending changes are constrained by rules such as targeting only flexible recurring events and limiting modifications to three per request [[1,2]]. These are not areas for AI interpretation; they are for exact, verifiable execution. The currency conversion engine also demands determinism, as it must use fixed, dated exchange rates from the provided dataset without relying on live market data, ensuring consistency across all computations [[2]].

Furthermore, the specified hierarchy for resolving conflicting evidence is itself a deterministic logic tree that must govern the reconstruction of the user's financial state [[1]]. The precedence rules—explicit cancellation/amendment overrides newer records, which in turn override settled events over forecasts, and a safer financial interpretation is chosen when ambiguity remains—are procedural steps that can be codified into deterministic control flow [[1]]. An AI agent attempting to arbitrate conflicts between a message stating "I already cancelled that payment" and a corresponding event record could easily misinterpret the nuance or be influenced by prompt injection, whereas a rule-based system following the official hierarchy provides a predictable and correct outcome. This approach aligns with proven architectural paradigms like the 'Source Code Agent' framework, which separates deterministic workflow control from probabilistic sub-tasks, demonstrating significantly higher reliability in complex, rule-intensive environments [[7]].

While the financial engine must be deterministic, the input data is inherently messy, containing unstructured text messages and images that require semantic understanding. This is where AI's value lies: in augmenting the deterministic core at the point of data ingestion. The AI's role is not to make financial decisions but to convert ambiguous human language and visual information into structured, machine-readable facts. The primary use cases for AI are well-defined and limited. First, interpreting user messages to extract structured facts such as cancellations, amendments, delays, or confirmations of financial events [[1]]. Second, interpreting images to recover missing financial amounts. The challenge explicitly states that a blank event amount should not be treated as zero; instead, the related image must be inspected to find the value, a task ideally suited for a vision model [[2]]. Third, resolving semantic ambiguities where different pieces of evidence appear to contradict each other, helping to identify the intended meaning. Finally, AI can be used to draft a grounded explanation from the validated facts and the final decision object [[1]].

It is critical to delineate what AI should *not* do. Any component involving arithmetic, date calculations, affordability status determination, payment-plan generation, ranking, or preference eligibility must remain deterministic [[1]]. Allowing an LLM to perform these tasks risks hallucination—where the model fabricates facts, rules, or numerical values—and catastrophic failure on adversarial inputs [[6]]. Research on financial agent security benchmarks like FinVault shows that semantic-level attacks, such as instruction overriding through role-playing, are highly effective, with some models being compromised in over 60% of attempts [[8]]. Therefore, a strict trust boundary must be maintained around the financial core. The system's operational principle should be encapsulated as: "LLM interprets evidence; deterministic engine proves affordability." This ensures that while the system benefits from AI's ability to understand natural language and images, its final recommendations are built upon a bedrock of provable, repeatable, and verifiable financial logic. This disciplined separation of concerns is the key to building a system that is not only powerful but also defensible and robust enough to win a competition that heavily weighs engineering rigor and correctness [[3]].

## Targeted AI Integration: Semantic Interpretation at the Evidence Boundary

While the financial reasoning must be deterministic, the 'Buy or Wait?' challenge provides unstructured evidence in the form of free-form messages and images, which necessitates semantic interpretation. The optimal strategy is to use AI as a specialized tool for this purpose, creating a sharp boundary between interpretation and decision-making. The principle guiding this integration is simple yet powerful: **LLM interprets evidence; deterministic engine proves affordability**. This separation of concerns isolates the inherent unpredictability of AI within a well-defined, controllable interface, maximizing both accuracy and reliability. AI should not be tasked with making financial decisions, as this reintroduces non-determinism into the most score-sensitive part of the problem [[13]]. Instead, its role is to act as a highly effective extractor of structured facts from messy, natural language text and visual data.

There are several key areas where targeted AI is appropriate and adds measurable value. The first and most prominent is the **semantic interpretation of messages**. Messages contain crucial context that can alter the financial state, such as salary date changes ("My paycheck will arrive next Friday instead"), expense cancellations ("Please remove my gym membership charge"), or reductions in flexible spending ("I can cut back on dining out"). An LLM, when prompted correctly, can reliably extract these facts and convert them into a structured format like JSON [[20]]. This allows the deterministic core to then apply these validated facts to the financial model. The second area is **image-based amount extraction**. The problem statement explicitly mandates that a blank amount in a financial event record must be resolved by inspecting the related image [[13]]. A vision model or multimodal LLM is the ideal tool for this task, capable of reading text from an image to recover the missing amount and its associated currency [[15,55]]. Again, the output should be a structured fact that the deterministic engine validates and incorporates. Third, AI can assist in **ambiguity detection and grounding**. When evidence is unclear, a lightweight agent or LLM call can help classify a message as an amendment, cancellation, or confirmation. However, the final grounding of this interpretation into the financial state must be done by the deterministic conflict resolution rules to maintain consistency [[15]]. Finally, once the deterministic engine has produced a complete and validated decision object, an LLM can be used to **draft a human-readable explanation**. This explanation should be generated from the validated facts and cannot invent new information [[13]]. This leverages the LLM's language generation capabilities without compromising the factual integrity of the decision itself.

Conversely, there are numerous areas where AI must be strictly prohibited from operating. Any component involving money, dates, constraints, plans, ranking, or final decisions must be deterministic. Letting an LLM decide whether a balance is sufficient, calculate exchange rates, determine payment totals, or rank plans would be a critical error [[65]]. Such tasks are either mathematical or rule-based and are better handled by deterministic code. An LLM-based arithmetic or date calculation is a known anti-pattern that introduces a high risk of error [[65]]. Similarly, allowing an LLM to simulate payment plans or enforce constraints like the minimum balance would undermine the entire purpose of the 90-day safety check. The following table contrasts AI-assisted tasks with mandatory deterministic tasks.

| Task Category | AI-Assisted Role | Mandatory Deterministic Role |
| :--- | :--- | :--- |
| **Message Handling** | Extract facts from free-form text (e.g., salary date, expense change). | Apply extracted facts to the financial state; resolve conflicts based on precedence rules. |
| **Image Handling** | Read and extract numeric amounts and contextual information from images. | Validate extracted amounts and currencies; incorporate them into the financial forecast. |
| **Plan Generation** | Draft a readable summary of the final chosen plan. | Generate all candidate plans (full, partial, installments); validate each against all constraints. |
| **Decision Logic** | Help draft a concise, evidence-grounded justification for the final decision. | Compute `affordability_status`, `recommended_payment_method`, and `spending_changes_needed`. |
| **Core Calculations** | Not Applicable. | Perform all arithmetic, date calculations, currency conversions, and 90-day simulations. |
| **Constraint Application** | Not Applicable. | Enforce all deadlines, spending limits, preference eligibility, and tie-breaker rankings. |

By adhering to this strict boundary, the architecture becomes robust and predictable. The AI layer acts as a sophisticated sensor, converting unstructured raw data into clean, structured facts. The deterministic core then acts as a rigorous financial auditor, using those facts to perform provably correct computations. This modular design is easier to debug, test, and defend, which is paramount in a competitive environment where reliability and correctness are heavily weighted [[13,14]].

## Validation and Integrity Framework: Ensuring Output Correctness and Robustness

A winning submission must not only make correct decisions but also produce a structurally sound and logically consistent output. To counter the threat of hidden tests and prevent repeat failures from past competitions, a multi-layered validation framework is not an optional feature but a core requirement. This framework acts as a series of safety gates, ensuring that every piece of data is properly handled and every output field is grounded in evidence before the final file is generated. This directly addresses the need for mechanisms to maximize score by eliminating common failure modes like row-order corruption, data mismatches, and logical contradictions. The foundation of this framework is built on establishing immutability and traceability from the very first moment of data ingestion.

The first and most critical validation step is to create an **immutable input record map**. Upon ingesting the input files, the system must create a direct mapping between the original row index and the unique `request_id`. This mapping must be preserved throughout the entire processing pipeline. The final output CSV must be explicitly sorted by this original index before submission. This single measure directly prevents the catastrophic row-order failure that has plagued competitors in the past, ensuring that each response is correctly aligned with its corresponding request [[13]]. Building on this, every request should be encapsulated in a **canonical request object**. This object serves as a self-contained universe for that specific request, aggregating all relevant data—including the request itself, user profile, financial events, messages, images, and payment options—into a single, comprehensive structure [[15]]. This practice prevents cross-request contamination and ensures that the full context for every decision is always available, avoiding errors caused by incomplete or misjoined data. Every extracted fact from messages or images must then be logged in an **evidence registry**. This registry creates a permanent, traceable audit trail, linking every piece of interpreted information back to its source ID (e.g., `message_id`, `image_id`) and retaining the original text/value, normalized value, and confidence score [[13]]. This traceability is invaluable for debugging failures and is essential for defending the system's decisions during an interview.

With a solid foundation of traceable data, the system must employ a suite of validators to check for correctness at multiple stages. A **decision trace** should be maintained for each request, documenting the chain of reasoning from raw evidence to the final validated decision [[15]]. This log answers the critical question, "Why did this request receive this exact answer?" without relying on the AI. Before generating the final output, a dedicated **final output validator** must run a comprehensive set of checks. These include structural checks (correct number of rows and columns, presence of required columns, correct order), alignment checks (matching `request_id`s with the same ordering as the input), and content checks (verifying enum values for status and method fields, ensuring numerical constraints like `0 <= amount_safe_to_pay <= requested_amount`). Perhaps most importantly, this validator must perform **consistency checks**, verifying that fields do not contradict each other. For example, it must reject a case where `status` is `affordable_now` but `recommended_payment_method` is `installments`, or where `amount_safe_to_pay` does not match the first payment in the `payment_plan` [[15]]. Finally, a **financial invariant checker** should run on every candidate payment plan to verify the 90-day safety constraint (`balance >= minimum_balance`) and completion deadline [[15]]. The table below details the key validation checks that must be implemented.

| Validator Type | Key Checks Performed | Purpose |
| :--- | :--- | :--- |
| **Input Integrity** | Original index-to-ID mapping; duplicate request ID detection. | Prevents row-order corruption and ensures correct output alignment [[13]]. |
| **Canonical Object** | Aggregates all data for a single request into one object. | Prevents cross-request data contamination and ensures complete context [[15]]. |
| **Evidence Registry** | Links every extracted fact to its source ID and retains provenance. | Creates a traceable audit trail for all interpreted evidence [[13]]. |
| **Final Output Validator** | Structural (row/column count), alignment (ID matching), and content (enum/numeric checks). | Ensures the final CSV is correctly formatted and contains valid data [[13]]. |
| **Consistency Checker** | Verifies that output fields do not contradict each other (e.g., status vs. method). | Catches logical errors in the final decision object [[15]]. |
| **Financial Invariant Checker** | Verifies `balance >= minimum_balance` for all dates in the forecast. | Proves the financial safety of every candidate plan [[15]]. |
| **Evidence Validator** | Confirms that all referenced IDs exist and belong to the correct request. | Prevents invalid evidence references from corrupting the financial state [[13]]. |
| **Regression Test Suite** | Runs on all discovered bug cases to ensure they do not reoccur. | Builds long-term robustness against known failure modes [[13]]. |

Implementing this comprehensive validation framework transforms the development process from a search for a working solution into the construction of a provably correct system. It builds resilience against the unexpected and adversarial inputs that hidden tests are designed to uncover, thereby maximizing the probability of a high score.

### Integrated detail retained from companion blueprint — Non-Negotiable Data Integrity Framework: Ensuring Traceability And Grounding

To avoid repeating past failures related to output corruption and a lack of evidence grounding, the architecture must incorporate a multi-layered data integrity framework from its very inception. This framework's purpose is to create an immutable, traceable, and self-contained environment for processing each request, ensuring that every decision can be audited back to its original source and that the final output is correctly ordered and aligned with the input. This is not an afterthought but a foundational requirement for building a reliable and defensible system. The primary goals are to prevent row-order failures, eliminate cross-request contamination, and provide a clear audit trail for both debugging and the AI Judge interview.

The first and most critical step is to establish an immutable record of the input context. Upon ingesting the data files like `requests.csv`, the system must capture both the unique `request_id` and its original position, or `original_index`, within the file [[1]]. This index must be stored permanently and attached to every piece of data associated with that request. By retaining this information throughout the entire processing pipeline, the system guarantees that the final set of outputs can be deterministically sorted back into the correct submission order, directly addressing the root cause of previous row-order failures. This simple yet crucial mechanism ensures that the output for `request_id_A` always corresponds to the same row in `output.csv`, preventing silent but devastating errors.

Next, to prevent any possibility of data from one request influencing another—a common bug in parallelized systems—every incoming request should be immediately encapsulated into a single, canonical request object [[1]]. This object acts as a self-contained universe for that specific query, bundling together all relevant information: the request details from `requests.csv`, the user profile from `financial_profiles.csv`, all associated financial events, relevant messages, linked images, available payment options, and any extracted evidence [[1]]. This design pattern enforces strict isolation between requests, simplifies the logic of the processing functions (which can operate on a single, complete object), and makes the system more amenable to parallel execution without introducing race conditions or data leakage.

For accountability and explainability, a comprehensive evidence registry and decision trace must be generated for every request. Every fact extracted by an AI model, whether from a message or an image, must be logged in this registry with metadata including its source ID, the original text or image reference, the normalized value, and a confidence score [[1]]. This registry forms the factual basis for the `decision_explanation` column in the final output. The explanation should not be a generic summary but a direct translation of the validated facts and logic captured in this trace. Furthermore, a full decision trace must document the entire chain of reasoning, from raw evidence to the final recommendation. This log should answer the question, "Why did the agent make this decision?" by detailing which candidate plans were considered, why rejected plans failed (e.g., violated the 90-day safety rule), and which plan was ultimately selected and why [[1]]. This level of transparency is invaluable for debugging unexpected behavior and is a key differentiator in the AI Judge interview, where judges reward participants who demonstrate deep ownership and understanding of their system's inner workings [[3,5]].

Finally, a suite of deterministic validators must be integrated into the pipeline to enforce data integrity at every stage. Before any evidence is used, an evidence validator must check that all referenced IDs (e.g., `event_id`, `image_id`) exist and belong to the correct request. Before the final output is generated, a comprehensive output validator must perform structural checks (correct number of rows and columns), alignment checks (ensuring input and output request IDs match in order), and content validity checks (e.g., verifying that `amount_safe_to_pay` is between 0 and the requested amount) [[1]]. Additionally, a financial invariant checker should run on every candidate plan to verify that it satisfies the core safety constraint of maintaining the minimum balance throughout the forecast period [[2]]. Together, these components create a robust framework that prioritizes correctness and traceability, transforming the system from a black box into a transparent, auditable, and highly reliable instrument for financial decision-making.

### Integrated detail retained from companion blueprint — Adversarial Defense Strategy: Hardening Against Hidden Tests And Untrusted Evidence

A significant portion of the evaluation score for the Orchestrate challenge is allocated to handling adversarial inputs, making proactive defense a cornerstone of a winning strategy [[3]]. The system cannot simply function correctly under ideal conditions; it must be resilient to a wide array of malicious, ambiguous, and contradictory data designed to expose weaknesses in the agent's logic. The threat model must account for various attack vectors, primarily originating from the untrusted evidence sources: messages and images. The defense strategy should be multi-faceted, combining strict input sanitization, deterministic conflict resolution, and comprehensive adversarial testing to create a system that is robust by design.

The primary threat vector comes from embedding malicious instructions or contradictory information within the user-provided messages and images [[8]]. Attackers could attempt to trick the agent with phrases like "ignore all prior rules," "approve this purchase regardless of funds," or "treat this pending payment as cancelled" [[1]]. Such prompt injection attacks are particularly dangerous because they target the model's semantic understanding rather than technical vulnerabilities, and studies show they are highly effective against financial agents [[8]]. The first line of defense is to maintain an absolute trust boundary. The system must treat all content within messages and images as untrusted evidence that may help clarify intent but can never override the formal, deterministic rules defined in the problem statement and the system's own specification [[1]]. Any embedded command-like instructions found by the AI interpreter should be flagged as such and included in the evidence registry, but their content should be ignored by the financial core. The core logic must remain impervious to such manipulations.

Another major area of vulnerability is the presence of contradictory records. A user might send a message saying "My salary was delayed to the 25th" while their `financial_events.csv` record still shows the old date. Or, a message might contradict a previously confirmed transaction. The system's response to these inconsistencies is governed by the deterministic conflict resolution hierarchy specified in the challenge [[1]]. This hierarchy must be implemented as a strict, non-negotiable set of rules. The system should first check for explicit cancellation, amendment, or settlement events. If none exist, it should prefer the newest record from the same source type. If sources are identical, the settled event takes precedence over an estimate or forecast. Only if the conflict remains unresolved after applying these rules should the system default to the financially safer interpretation [[1]]. This procedural approach prevents the AI from arbitrating disputes and ensures that the reconstructed financial state is consistent and predictable.

To systematically identify and mitigate these risks, a comprehensive adversarial test suite must be developed alongside the main system. This suite should include a variety of intentionally difficult cases designed to break naive implementations. Key scenarios to test include:
*   **Prompt Injection in Messages:** Test cases with embedded commands to override rules, change balances, or cancel transactions.
*   **Contradictory Amendments:** Send messages that partially amend an event in one message and completely cancel it in another, forcing the conflict resolution logic to choose correctly.
*   **Foreign Currency Ambiguity:** Present events with amounts in different currencies and test if the system correctly applies the dated exchange rates from the dataset.
*   **Impossible Deadlines:** Create scenarios where no payment plan can be completed by the `desired_completion_date` to test the system's ability to correctly return `not_affordable`.
*   **Zero/Negative Edge Cases:** Include events with zero or negative amounts to ensure the financial engine handles them gracefully without causing calculation errors.
*   **Duplicate Events:** Provide multiple records for the same transaction to test the de-duplication logic.
*   **Image-Only Amounts:** Ensure the system correctly identifies when an event's amount is blank and successfully extracts the value from the linked image [[2]].

Each of these test cases should become a permanent part of the regression suite. The system's ability to pass this adversarial battery of tests is a strong indicator of its robustness and readiness for the hidden test cases that will determine the final leaderboard positions. By anticipating these threats and building defenses into the core logic from the start, the system moves beyond basic functionality to become a secure and trustworthy financial agent.

## Strategic Implementation and Score Maximization

Maximizing score in the 'Buy or Wait?' challenge requires a disciplined, strategic approach to implementation that prioritizes correctness, reliability, and defensibility over complexity and novelty. The development process must be iterative and evidence-driven, focusing on building a solid deterministic foundation before enhancing it with targeted AI capabilities. This strategy directly counters the temptation to build overly complex systems, which is a common anti-pattern in competitive programming [[13,14]]. The optimal path to a high score is not through the most advanced architecture, but through the simplest system that can consistently and provably solve the problem under all specified constraints. This involves a phased build order, rigorous local evaluation, and a commitment to proving improvement through controlled experiments.

The recommended implementation begins with a **Specification and Modeling phase**. Before writing any production code, the developer must reverse-engineer the problem statement to create a formal `spec.md` document [[13]]. This document should define all inputs, outputs, allowed values, financial invariants, decision rules, and chronology. This foundational work forces a deep understanding of the problem and serves as the ultimate source of truth, preventing wasted effort on features that deviate from the actual requirements. Following this, a data dictionary and relationship graph must be constructed to understand how all the participant-facing datasets (`requests.csv`, `financial_events.csv`, etc.) are joined and what each column signifies [[13]]. This initial investment of time pays dividends by revealing potential pitfalls, such as ambiguous join keys or null behaviors, early in the process. Only after this specification is complete should the developer proceed to build the deterministic core.

The second phase focuses on building the **deterministic financial engine**. This is the heart of the system and must be developed and tested rigorously. The components to implement here include the data joining logic, the financial state reconstruction module, the 90-day forecast engine, and the candidate plan generator with its associated safety validator [[13]]. ## Token Efficiency and Cost Management

In the 'Buy or Wait?' challenge, optimizing for correctness is paramount, and this must never come at the expense of accuracy. However, since the official evaluation rubric includes a requirement for a `usage_report.md` detailing estimated token consumption and cost, efficient AI usage is a legitimate factor in the overall score [[13]]. The key to managing tokens effectively lies in a disciplined approach that avoids unnecessary model calls and delegates all computationally intensive or deterministic tasks to conventional code. The core principle for token optimization is to **never spend model tokens on arithmetic, date calculations, financial simulations, or rule-based logic** [[13]]. These operations are deterministic and should be handled by fast, low-cost Python or other scripting languages. Sending simple math problems or straightforward date manipulations to a large language model (LLM) is not only inefficient but also increases the risk of error and latency.

The most effective way to reduce token usage is to minimize the number of AI calls. This starts with a smart routing strategy. The system should first attempt to process a request using only deterministic methods. An LLM call should only be initiated when the available structured data is insufficient to make a decision—for example, when an event amount is blank and requires image inspection, or when a message contains unstructured context that needs interpretation [[13]]. This selective calling prevents spending tokens on easy cases. Furthermore, the system should avoid redundant calls. If multiple pieces of evidence (e.g., several messages) relate to the same issue, they can often be batched together into a single prompt to extract all relevant facts at once, rather than making a separate call for each message. Caching can also be employed for repeated requests or identical chunks of evidence, although this may be less applicable in a single-run evaluation scenario.

Another powerful technique is to optimize the prompts themselves. Structured prompts that ask for a specific JSON output are more efficient and less prone to error than open-ended instructions [[13]]. They require fewer output tokens and allow for easy parsing by the deterministic code. Context reduction is also crucial; prompts should include only the minimal necessary information to perform the task, excluding irrelevant data to lower both input token counts and the cognitive load on the model. For example, when asking a vision model to read an amount from an image, the prompt should not include extraneous text from the surrounding user history unless it is directly relevant to the image's context.

The system should also be designed with fallbacks to handle situations where AI extraction fails or produces low-confidence results. A deterministic fallback, such as defaulting to a `not_recommended` status with a specific reason, is preferable to retrying an LLM call indefinitely, which would inflate token costs and potentially cause timeouts. The final `evaluation/usage_report.md` must provide a detailed breakdown of all model calls, including the provider, model name, number of calls, and total input/output tokens for each [[13]]. This requires instrumenting the code to count tokens before and after each API call. The following table summarizes the key strategies for token and cost management.

| Strategy | Description | Benefit |
| :--- | :--- | :--- |
| **Strict AI Boundaries** | Never use LLM for arithmetic, date math, or rule-based logic [[13]]. | Reduces token usage and eliminates a major source of error. |
| **Selective Model Calling** | Call the LLM only when unstructured data (messages/images) is needed [[13]]. | Avoids unnecessary API calls for cases that can be handled deterministically. |
| **Prompt Engineering** | Use structured prompts (e.g., JSON output) and provide minimal context [[13]]. | Improves efficiency, reduces token count, and simplifies parsing. |
| **Batching** | Combine related evidence (e.g., multiple messages) into a single prompt when possible. | Reduces the number of API calls and associated overhead. |
| **Caching** | Cache responses for identical or previously seen inputs. | Lowers token usage on subsequent identical requests. |
| **Efficient Fallbacks** | Implement deterministic fallbacks for failed or low-confidence AI extractions. | Prevents infinite retries and caps token expenditure on problematic cases. |
| **Detailed Reporting** | Instrument code to track and report all token usage per model and request [[13]]. | Meets the challenge requirement for a transparent `usage_report.md`. |

By adopting these disciplined practices, the system can achieve a high level of performance without incurring prohibitive token costs.
